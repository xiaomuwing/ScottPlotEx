## 3. 数据通路的设计差异（决定长期可行性）

| 方案 | 数据存放 | 内存随时间 | 跨线程调用 | 是否适合 8 小时 × 2.88 亿点 |
|---|---|---|---|---|
| S1 | 控件自带缓冲（无上限） | 持续增长 | 每批一条窗口消息 | ✗ 消息队列会被淹没、内存无上限 |
| S2 | 控件自带缓冲（无上限） | 持续增长 | 无（UI 线程） | △ 不淹消息队列，但内存与绘制量随时间线性增长 |
| S3 | 自建定长数组（滑动窗口） | **有界** | 无（后台直写） | ✓ 内存与绘制量恒定 |
| S4 | DataStreamer 定容量环形 | **有界** | 无（UI 线程写入） | ✓ 内存恒定，绘制量 = 容量 |
| S5 | DataLogger（保留全部点） | 持续增长 | 无（UI 线程写入） | △ 渲染自动抽稀，但内存随运行时间增长，8 小时需定期清理 |

## 4. 最佳实践（本次实测推荐）

**S3　S3 自建定长缓冲 + 只画窗口尾部（后台直写，无编组）**：目标 10,000 点/秒 全部达成（丢点 0），CPU 80% 单核，UI 延迟 p95 13.1 ms，帧率 64.2 FPS。

推荐写法要点：

1. **不要逐点跨线程调用控件 API**（S1 的失败模式：每个点一条窗口消息 → 消息队列被淹没、界面定时器与重绘被饿死）；
2. 采集线程写**自建定长缓冲**（预分配数组 + 写指针），UI 线程只按帧更新“画哪一段 + 视图范围”，数据接入与渲染完全解耦；
3. 曲线只画**可见窗口内的点**（`Signal.MinRenderIndex/MaxRenderIndex`，或 `DataStreamer` / `DataLogger` 的原生视图）；
4. 视图范围按帧统一设置（`Axes.SetLimits`），Y 轴用固定范围或低频自动缩放，避免每帧全量扫描；
5. 每帧批量写入（约 17 点/曲线/帧 @1000 点/秒、60 FPS），不要逐点刷新。

示例（把采集线程与 UI 解耦，10 条曲线各 1000 点/秒）：

```csharp
// 采集线程：写自建滑动窗口，不碰 UI、不碰控件
double[] buffer = new double[60,000];   // 每条曲线 60 秒
int written = 0;
void OnSample(double value)
{
    if (written == buffer.Length)          // 整体前移，保持定内存
    {
        Array.Copy(buffer, 1, buffer, 0, buffer.Length - 1);
        written--;
    }
    buffer[written++] = value;
}

// UI 线程：每帧只做两件事——告诉 Signal 画哪一段、设置视图窗口
Signal signal = plot.Add.Signal(buffer, period: 1);   // buffer 是上面那个定长数组，只需建一次
signal.MinRenderIndex = 0;
signal.MaxRenderIndex = written - 1;
plot.Axes.SetLimits(written - 60_000, written, yMin, yMax);
plot.RequestRender();
```

## 5. 测量说明与局限

- 视图统一为“最近 60 秒 + 固定 Y 范围”，目的是隔离“写入通路”的差异；真实应用中若开启每帧自动缩放（Y 轴全量扫描）会额外增加每帧成本。
- 内存增量是 2 分钟窗口内的粗略值（受 GC 时机影响）；判断“内存是否有界”应以第 3 节的设计差异为准，而不是这两个数字。
- S1/S2 用控件的**单曲线** API 承载全部 10,000 点/秒（控件目前是单曲线设计，无法承载 10 条曲线），用来测控件自身通路的极限；
  S3~S5 承载完整的 10 条曲线，这才是“10 条曲线 × 1000 点/秒”的真实形态。
- FPS = 实际渲染次数 / 秒（`RenderManager.RenderCount` 差值）；强制整帧耗时为 UI 线程上 3 次 `Refresh()` 的中位数。
